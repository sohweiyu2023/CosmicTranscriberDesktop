# Conservative pending-request recovery (proposed follow-up)

This follow-up protects the normal UI/coordinator path within the same existing source/request/output cache context. It is not provider idempotency or global exactly-once processing. Changing output/configuration, copying files, storage loss or manual cache deletion can escape that context; none is a recommended recovery procedure. The lower-level client callback remains optional for callers outside the coordinator. The guard cannot reconstruct uncertain attempts made by pre-ledger versions.

Before its single paid POST, the client awaits a coordinator callback with the actual generated client request ID. The callback creates a fixed-schema chunk intent using CreateNew and Flush(true), while existing work/cache leases remain held. The intent stores only index, generated attempt/client ID, schema and UTC time—no credential, source path, prompt, audio or transcript. A write/callback failure aborts SendAsync; a partial file is retained and blocks later dispatch.

All pending markers are checked before any new paid work in the context. An unresolved, malformed, unreadable or unmatched marker blocks the run. Age never clears an intent. HTTP errors including400/401/429, transport failures, malformed bodies and timeouts retain the intent; they do not establish no charge. Such failures stop the queue systemically. Cancellation likewise retains unresolved intent unless the accepted response can be saved and reconciled first.

After acceptance, the completed checkpoint, attempt GUID and actual client ID are saved under the existing bounded storage-only token. The new checkpoint checksum covers those identity fields as well as the response. Only rereading a valid checkpoint bound to that exact intent permits deleting it. An older valid checkpoint cannot corroborate a newer intent. Legacy checkpoints retain their old checksum and stable work-directory key; they can be reused normally with no pending marker but never clear one. The cache-key schema was not bumped or forked.

A crash before send can leave a conservative false positive. A crash during upload, after response or during checkpoint persistence keeps the intent. A restart after the bound checkpoint is durable can reconcile it and reuse accepted work with zero new HTTP calls. Delete failure keeps evidence blocked. Invalid response evidence is preserved when an intent exists. Existing storage leases prevent competing application runs/clear operations; CreateNew is a second reservation gate. Cache clear preflights every work directory before deleting anything and refuses any pending marker, even empty/corrupt/unreadable ones. Old application versions treat the new marker as an unexpected cache item and refuse use/clear rather than silently removing it.

There is deliberately no automatic retry, age-based unlock, free-failure inference or new credential persistence. **No ordinary user resolution/override UI exists yet.** If an outcome cannot be corroborated by a matching accepted checkpoint, preserve the cache and review the existing attempt and possible charges; do not delete markers or clear the cache as a workaround. A maintained, explicit review workflow is still required before this can be treated as an everyday recovery feature. No provider lookup API or billing reconciliation guarantee is claimed.

Offline tests use only synthetic audio and fake HTTP. Cases include pre-send interruption, upload uncertainty, accepted response with checkpoint write failure, durable checkpoint before reconciliation, old/legacy mismatch, attempt checksum tampering, partial/corrupt/locked markers, delete failure, competing reservations, all-directory clear preflight, cache lease contention, cancellation just after acceptance and later-chunk pending evidence blocking earlier new dispatch. A deliberately weakened attempt-binding negative control must fail the stale-checkpoint assertion. These simulated crash states do not certify physical power-loss durability or native UI behavior.
